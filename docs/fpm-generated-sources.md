# Generated gFTL sources

The gFTL templates need include files generated by the upstream CMake/m4 rules.
gFTL-shared also configures Fortran modules from `.F90.in` templates. The
playground stores these generated files as audited, checksum-locked assets in
[fpm_catalog/generated](../fpm_catalog/generated). Preparation copies them into
the pinned source trees; it does not run CMake, m4, or repository build scripts.

The recorded source revisions are:

| Source | Pinned revision | Generated files |
| --- | --- | --- |
| [gFTL](https://github.com/Goddard-Fortran-Ecosystem/gFTL/tree/4af86210b6cc6ac46d3298b6861571aa26bd6acc) | `4af86210b6cc6ac46d3298b6861571aa26bd6acc` | 151 generated include files, 147 staged upstream include files and one integer-vector instantiation |
| [gFTL-shared](https://github.com/Goddard-Fortran-Ecosystem/gFTL-shared/tree/8009755e846560fbb389c01d76e013ddf14a7f98) | `8009755e846560fbb389c01d76e013ddf14a7f98` | Four configured v2 vector modules |

These packages use Apache-2.0 licenses. Original sources, license files and
notices remain in the downloaded source trees. The integer-vector wrapper
instantiates the upstream implementation; it adds no container algorithm.
The two disjoint include namespaces are staged under one include root for immutable dependency exports. Original directory trees remain intact. The catalog describes gFTL-shared as a selected subset, rather than advertising
every upstream instantiation.

## Reproduce the assets

Extract the exact pinned source archives, install GNU m4, and run:

```text
python xgenerate_gftl.py --gftl-source PATH_TO_GFTL --shared-source PATH_TO_GFTL_SHARED --check
```

The serial pFlogger recipe uses a separate gFTL-shared asset adding the v2
IntegerString, StringInteger and StringUnlimited maps. Add `--pflogger` to
generate or check that variant. The original vector-only asset and its cache
identity remain unchanged. Both variants are included in downloaded projects.

fdict uses three generated Fortran modules from its pinned Fypp templates.
With Fypp 3.2 installed, reproduce the standard-kind, rank-five configuration:

```sh
python xgenerate_fdict.py --source PATH_TO_FDICT --check
```

FGSL uses the complete configuration header produced by its upstream Autoconf
probes with GSL 2.8. The catalog stores that header as `config.inc`; guarded
patches change only the include filename in the original and staged Fortran/C
sources. On GNU/Linux LP64, with GNU Fortran, GCC, GSL development files,
pkg-config, Autoconf, Automake and Libtool installed, reproduce it with:

```sh
python xgenerate_fgsl.py --source PATH_TO_FGSL --check
```

This FGSL configuration targets GNU/Linux LP64 and GSL 2.8. A different ABI or
GSL version requires a fresh upstream configuration and a reviewed recipe.
Downloaded projects include the recorded configuration and patches, but still
need the compatible GSL development libraries installed locally.

## Configured CMake libraries

flibcpp, libMBD and dtFFT use small files generated during upstream CMake
configuration. The operator helper records the selected library sources and
Fortran preprocessor definitions through CMake's file API, and stores the
generated text with hashes of its original CMake/template inputs:

```sh
python xgenerate_cmake_packages.py flibcpp --source PATH_TO_FLIBCPP --check
python xgenerate_cmake_packages.py libmbd --source PATH_TO_LIBMBD --check
python xgenerate_cmake_packages.py dtfft --source PATH_TO_DTFFT --check
```

These configurations use GNU Fortran 16/GCC on Linux, CMake, OpenBLAS, MPICH
and FFTW development packages. The libMBD configuration is serial; dtFFT uses
the CPU/FFTW backend with input checks, without GPU or C/C++/Python bindings.
Both numerical packages require their native development libraries for local
builds. Include and linker flags may need adjustment on other installations.

The flibcpp Git archive has no release metadata, so its generated version uses
the upstream fallback. libMBD's version module explicitly identifies the pinned
commit with a `0.0.0-<commit>` suffix. Neither reports an inferred release number.
The catalog stages flibcpp's unchanged `.cxx` wrapper contents as `.cpp`, which
FPM 0.12 discovers; the original files remain in the downloaded source tree.

Audited assets can contain Fortran/C++ source and C-style configuration headers.
The same checksum, path, size and overwrite checks apply. Visitor preparation
copies these text files; CMake and repository build scripts are not executed.
Existing generated-source recipes retain their previous adapter identifiers
and compiled-library cache keys.

Omit `--check` to regenerate the assets for review. The generator records hashes
of its original inputs and follows the relevant upstream m4 expansions and
`configure_file` substitutions. It omits m4 diagnostic line markers to avoid
machine-specific paths and normalizes text to LF. Windows GNU m4 1.4.14 and
Linux GNU m4 1.4.19 reproduced identical assets. Package source-review records
retain the independent Linux generation check.

Each catalog recipe locks the complete asset checksum. Preparation also checks
the asset's repository, revision and input hashes, rejects paths outside the
source tree, and refuses to overwrite upstream files. Existing archive size
and file-count limits still apply after staging generated files.

## Sharing and local use

Generated dependencies use a source-recipe fingerprint in an otherwise unused
`PLAYGROUND_CATALOG_...` preprocessing macro. The existing shared-cache contract
includes that manifest setting, so changing the asset, selected source files,
manifest or preparation-adapter version changes the dependency identity.
Unfingerprinted repackaged sources and patched shared sources remain rejected.
Existing package definitions and cache keys are preserved.

Downloaded projects include the exact generated assets and reproduce the input
and asset checks locally. They do not require CMake or m4 to prepare these
packages. A new gFTL template instantiation still needs Fortran preprocessing
and the appropriate include directories; the supplied example instead uses
the catalog's compiled integer-vector module.

## DBCSR and 2DECOMP&FFT configurations

`xgenerate_cmake_packages.py` also records the pinned DBCSR serial CPU and
2DECOMP&FFT generic CPU configurations. Reproduce them in the documented GNU/Linux
toolchain with `dbcsr` or `2decomp-fft` as the package argument and `--check`.
The JSON records retain selected source lists, definitions and configuration
input hashes. Empty `files` maps mean no configured text files need installation.

DBCSR uses 96 original `.F` templates rendered with Fypp 3.2. Preparation checks
each rendered output hash and stages it as free-form `.f90`, preserving the
original templates. Simple identifier-only `USE ... ONLY` lists, including
continuations, are sorted to make Python-set output reproducible across Python
versions and operating systems. Renamed imports and other Fortran statements
are left untouched. Checksum-guarded staging edits repeat the base-hooks imports hidden in the CPP
include so FPM can order module compilation. The manifest allows legacy
implicit external BLAS/LAPACK procedures while retaining runtime and bounds
checks. The compiler uses `__FILE__` for diagnostic filenames.
MPI, OpenMP, accelerators, LIBXS and LIBXSMM are disabled; OpenBLAS supplies BLAS.
The supplied consumer checks serial block-sparse multiplication against MATMUL.

2DECOMP&FFT uses its built-in generic FFT backend and double precision, with
OpenMP disabled and MPICH supplying MPI. The optional empty version macro is
omitted, so upstream logging reports the Git version as unknown. Its checked consumer runs in one MPI
process. This configuration does not verify multi-process execution or scaling.
Local builds require compatible MPI headers/libraries and local include flags.

Reviewed catalog recipes may select up to **1,000 source files** per package.
Recipes created under the former 500-file profile retain that policy and their
existing cache keys; recipes using the 1,000-file profile also keep their keys.
The independent generated-asset limit stays at 500 staged files / 2 MiB. Public
repository limits and the 16 MiB archive / 64 MiB expanded-source limits are
unchanged. File count alone does not determine compile time or artifact size;
every selected package still needs a checked consumer and sandbox reuse test.

PSBLAS remains deferred. Its 809-source configuration now passes source
preparation, compilation and archiving after the reviewed index/feature flags,
legacy language settings, visibility-name fixes and shortened staging path.
The checked consumer fails to link because the pinned CMake library list omits
MINRES implementations referenced by its Krylov dispatcher. A four-file source
addition is proposed but has not passed verification. See its
[investigation](fpm-candidates/psblas/source-review.json).

## ENNUF inference example

The ENNUF recipe compiles the original `neural_net_mod` with an audited generated
model module. The example has two inputs, two ReLU hidden units and one output,
with fixed, illustrative REAL32 weights. It is not a trained scientific model.
The checked main exercises both active and clipped hidden units and compares
four predictions with independent calculations.

To reproduce the model asset, install `numpy==2.2.6`, extract the pinned ENNUF
archive, and run:

```sh
python xgenerate_ennuf.py --source PATH_TO_ENNUF --check
```

Generation uses the upstream Model, Dense and Activation APIs. It sorts imported
procedure names because the upstream generator gathers layer types in a Python
set. No network operations are changed. Visitors and downloaded projects use the
stored, checksum-locked Fortran asset; Python inference, NumPy, TensorFlow and
PyTorch are not needed at runtime. The original source tree, Crown copyright
notice and BSD license are retained.

The PSBLAS CMake configuration record captures `-D` feature and index-kind
settings from raw compile-command fragments, as well as structured definitions.
These flags are part of the reviewed manifest and source recipe; visitors do
not run CMake feature probes.

Large reviewed libraries can opt into `short_root` in their source recipe.
Preparation then uses `packages/0/p` for the extracted container, preserving its
contents, internal paths and archive lock. This avoids excessively long FPM
object names: PSBLAS otherwise produces an archive command of about 134 KB,
exceeding the 128 KiB single-argument limit on the sandbox's 4 KiB-page Linux
configuration when FPM invokes the shell. The [Linux execve manual](https://man7.org/linux/man-pages/man2/execve.2.html)
documents the per-string limit of 32 pages.
The shortened form is about 96 KB. Only the operator adapter supports this
option; public archive rules and file/size limits are unchanged.

## ParaMonte source-staging allowance

The operator may stage up to **128 MiB** for ParaMonte at commit
`93a9f4f472894115b9f15ac0c68490af719f44fb`, archive SHA-256
`7cbaacf1b28e7e65b78a46f838966d1a3e9bccd8e34c7daaa497412271c42518`.
Its original archive expands to about 62.4 MiB; copies of the configured
translation units take the prepared tree above the normal 64 MiB limit.

This is an explicit exception in an operator-owned catalog recipe. The package
pin and the checksums of [the allowance helper](../fpm_catalog_limits.py) and
[the isolated prebuild entry point](../xfpm_catalog_prebuild.py) must match.
The public extractor and execution worker retain their 64 MiB limit. Archive
downloads remain limited to 16 MiB, individual files to 16 MiB, and links,
unsafe paths, duplicate entries and excess file counts are still rejected.
Compilation time and memory limits are unchanged.

The prebuild entry point reuses the existing build procedure with a larger
prepared-bundle extractor in its own process. It is installed only for this
operator build. Existing compiler recipes, workers and library cache keys are
preserved. A larger source allowance alone does not establish that ParaMonte
compiles or runs; see the [current investigation](fpm-candidates/paramonte/source-review.json).

## C++ source wrappers

Current operator recipes may set `FPM_CXXFLAGS` for wrapped C++ sources. FTorch
uses this to match upstream's C++20 mode, Torch headers, CPU definitions and
C++ ABI. The setting contributes to that package's immutable cache identity.
Older adapter profiles reject it, as do recipes without an explicit source
wrapper or recipes using shared dependency graphs. Public requests cannot set
image environment variables. Existing recipes and their cache keys are retained.

## Serial pFUnit

[xgenerate_pfunit.py](../xgenerate_pfunit.py) configures the pinned pFUnit,
fArgParse, gFTL-shared and gFTL source trees with GNU Fortran 16 and CMake. It
uses the upstream assertion generator and configured container templates.
The exact four revisions are recorded in the script and the
[generation evidence](fpm-candidates/pfunit/generation-evidence.json).

The catalog uses the upstream `MAX_ASSERT_RANK=2` option: scalar, vector and
matrix assertions. MPI, OpenMP, robust/forked runners and Hamcrest are disabled.
The resulting assertion asset stays below the existing 2 MiB limit; the
default rank-5 configuration exceeds that limit. The package description makes
this scope explicit.

To regenerate on GNU/Linux with CMake, Python, m4 and GNU Fortran 16 installed:

```sh
python xgenerate_pfunit.py --pfunit-source PATH_TO_PFUNIT \
  --fargparse-source PATH_TO_FARGPARSE --gftl-shared-source PATH_TO_GFTL_SHARED \
  --gftl-source PATH_TO_GFTL
```

Use extracted trees at the exact pinned revisions. The script assembles the
submodules in a temporary directory; configuration needs no network access.
It writes checksum-locked JSON text assets with LF line endings. Add `--check`
to compare them without overwriting, or `--evidence FILE.json` to save a
separate operator configuration report. Repeated
generation reproduced both assets byte for byte. Visitors and downloaded
projects use those assets; their builds do not invoke CMake, m4 or Python.
The plain Fortran demonstration uses `TestSuite`, `TestMethod` and `TestRunner`
without annotation preprocessing. A separate
[negative control](fpm-candidates/pfunit/negative-control.json) verifies that a
deliberately failing assertion produces an unsuccessful program result while
reusing the compiled library.
