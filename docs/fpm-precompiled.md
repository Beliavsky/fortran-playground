## Selection and versions

The catalog balances general usefulness, popularity, and reuse by other packages. It covers numerical methods, machine learning, databases, geodesy, plotting, data formats, dates, files, command-line tools, and containers. Every entry has a short checked consumer program. Selection considers repository stars and a sample of 400 accessible FPM manifests from [Fortran-packages-list](https://github.com/Beliavsky/Fortran-packages-list); the [selection evidence](fpm-catalog-selection.json) records the dated sample and its limitations.

[fpm_catalog.json](../fpm_catalog.json) records exact commits, archive checksums, license declarations, descriptions, and the dated popularity/reuse sample. The stdlib entry uses its pre-generated `stdlib-fpm` branch rather than requiring Fypp during submissions. It is a pinned snapshot, not a promise to track the latest stdlib release. Upstream sources and license files remain in each package image. License declarations are recorded per package; they vary, including GPL for ferror and fortran_test_helper. Fortran-primes declares MIT in its manifest but its source headers also identify CC-BY-NC-4.0 components. The kinds manifest uses a placeholder license string; its LICENSE file specifies BSD-3-Clause. The short [example programs](../fpm_catalog/demos) live in this repository; `python xfpm_examples.py` regenerates the browser catalogs.

## Source links and local project downloads

Selecting an available package exposes **Browse pinned source**, linking to its exact GitHub commit, with a separate link to the build notes and patches below. For the main-program workflow, **Download main (.f90)** saves the current editor contents. **Download FPM project (.zip)** saves the current main, standard input when present, package/dependency locks, build settings, patches, and local preparation tools. It uses the package URL and revision fields actually associated with the main; selecting another menu entry without loading it does not change the exported dependency.

Extract the ZIP, install Python 3.12+, a local compiler, FPM 0.12 or later, and any native libraries listed in its README. Then run:

```text
python -m pip install -r requirements.txt
python run.py
```

The first local run downloads and checks the pinned archives, prepares dependency manifests, applies recorded catalog patches, writes the final path-based `fpm.toml`, and compiles/runs the main locally. Later runs preserve prepared sources and any local edits. `python run.py --build-only` compiles without running; `--prepare-only` downloads/prepares sources without compiling. The runner applies the recorded compiler/link flags, so use it for subsequent builds too. Native system libraries are not installed automatically. The default compiler is gfortran; GNU-specific catalog flags must be adjusted before using another compiler family. Plotting also requires NumPy and Matplotlib locally.

These ZIPs are **not offline source bundles** and contain no precompiled hosted library. The dependencies download on the user's machine, and first local builds of large packages can take several minutes. Custom GitHub URLs can also be exported; their transitive dependencies resolve on the first download rather than using a catalog lock. Downloads are assembled in the browser, use no execution allowance, and work without an available FPM execution service. The download tools load only when requested.

## Catalog-specific build adaptations

Neural-fortran uses release **0.22.0**: the investigated current revision and release 0.23.0 fail GNU 16 compilation in the rank-remapping output accessor. The example trains a small dense network on generated observations without downloads or multiple images. Simulated-annealing uses release **1.2.0**, avoiding the newer manifest's list-valued library type unsupported by FPM 0.12.0. Polyroots and simulated-annealing use pinned native BLAS/LAPACK libraries. SQLite uses a pinned native SQLite library and an in-memory database in its example. Databases created in a job are disposable, like other sandbox files.

**SQLite wrapper fix:** this pin's `sqlite3_finalize_` C wrapper discards SQLite's status and returns an uninitialized local variable. A checksum-guarded catalog edit assigns the return value to `rc`. The exact edit and original source checksum are recorded in `catalog_patches`. The example checks statement finalization and database closure as well as the query result. The upstream archive pin/checksum is preserved separately.

Packages that need extra build inputs record them in `fpm_catalog.json`. The operator-only [catalog adapter](../fpm_catalog_build.py) installs exact Debian versions of BLAS/LAPACK/ARPACK where needed and supplies OpenMP/link flags. It resolves selected registry dependencies to checksummed GitHub archives, substitutes an explicit numeric version for literal `VERSION` placeholders, and translates the selected OpenMP metapackage before producing the offline source bundle. Quaff's GitLab dependencies use verified author-maintained GitHub mirrors, with compatible dependency revisions explicitly locked. ForPCA likewise locks compatible dependency versions. LightKrylov uses the catalog's generated stdlib snapshot and checked older FACE archive, with preprocessing enabled and MPI disabled. Its image uses external BLAS/LAPACK through the stdlib macros and compiles functions/data into separate sections so the linker can remove unused routines. This keeps the checked consumer executable under the existing 16 MiB file limit; compiler/runtime checks remain enabled. This does not enable arbitrary registry, GitLab, native-library, environment, or patch requests from visitors.

The adapter's checksum and per-package settings enter that package's cache key. Existing packages without these settings retain their library keys. Native system libraries reside in the package image; their bytes are excluded from the logical artifact figures below.

**SpecialMatrices workaround:** GNU Fortran 16.2 encounters an internal compiler error in selected `do concurrent` loops in this pin. The catalog applies checksum-guarded edits to the Strang matrix-product loop and the Poisson2D sine-transform and multiple-right-hand-side solve loops, using ordinary sequential loops with the same operations. The exact original file checksums and replacements are recorded in `catalog_patches` and applied by [the patch helper](../fpm_catalog_patches.py). The consumer checks diagonal solves, multiple-column Strang products, and Poisson2D solves. Original upstream archive checksums remain recorded, and normal compiler/runtime checks stay enabled. These are playground build workarounds, not upstream fixes.

**ForPCA example:** this pin returns the full principal-direction basis even when one component is requested. The example checks the leading direction and explicitly projects centered observations and reconstructs them, rather than relying on the package's scores/reconstruction fields. Its manifest license placeholder is clarified from the upstream BSD-3-Clause LICENSE file. SpecialMatrices also has a placeholder in its manifest; its README declares BSD-3-Clause.

## How reuse works

Each catalog library is built ahead of time using GNU Fortran **16.2.0**, FPM **0.12.0**, and the same debug profile and base compiler flags as normal package jobs, plus the explicitly recorded catalog-specific build settings above. A separate immutable image contains its sources, dependency revisions, module files, object files, and library archive. Selecting that exact repository/commit in **My main program** mode reuses the image and compiles/links your edited main program. Results explicitly say whether the library was reused.

Debug symbols are removed from precompiled dependency objects and archives to keep linked executables within the existing 16 MiB file limit. Runtime checks remain enabled; your main program retains its debug information. Backtraces inside a cached dependency may therefore have less detail than a local debug build.

All 83 packages passed the changed-main sandbox check, including a returned PNG for pyplot-fortran. The recorded compile/link checks took about 0.15 to 7.88 seconds. Their logical library artifacts total about 1,911 MiB; this excludes compiler layers, native system libraries, sources, and main executables and is not a compressed storage or billing measurement. See [the recorded validation](fpm-precompiled-validation.json).

Every job receives its own disposable filesystem copy. User code cannot update the published cache or another user's files. There is no shared writable build directory or package download during a cache hit. The normal job admission, CPU/memory bounds, network restriction, build/run timeouts, and output limits still apply. A changed main still needs compilation/linking; precompilation does not remove compiler/package limitations.

Other compilers, unlisted revisions, arbitrary package URLs, and the package's own Build/Run/Test workflow use clean builds. A cache is never reused across compiler versions or workflows. One catalog package is selected at a time; combining several catalog dependencies is not supported. The ordinary source playground and local tools do not load these images.

The hosted Python runner also benefits automatically when `--fpm URL --revision COMMIT --main FILE` selects a catalog pin with GNU 16. Its output reports library reuse, including in terse mode.

## Build, verify, and deploy

Use an authenticated Python environment containing [requirements-fpm.txt](../requirements-fpm.txt). From this repository root:

```powershell
python -X utf8 xprecompile_fpm.py
```

This builds and publishes package images, without changing the running API. First builds of LAPACK and stdlib can take several minutes. Offline prebuilds have a separate one-hour build allowance, 2 CPUs, and 4 GiB memory; this does not increase the limits for visitor jobs. They run without network access or secrets and compile as an unprivileged user. Sources are downloaded, bounded, and checked before entering the sandbox.

Before publication, the builder starts another sandbox with the ordinary public resource limits, changes executable Fortran statements in the main program, and checks both its output and reuse of library artifacts. Plotting must return a PNG. A failed package stops a complete catalog build from reporting success. Reports and reusable image references are stored locally in ignored `.fpm-audit-cache/precompiled.json`. Published libraries can also be recovered by their deterministic names when that local report is missing.

```powershell
python -X utf8 xdeploy_fpm.py --owner-secret p2f-owner
```

The deployment command processes the catalog incrementally. When the library key, worker version, and example source match a verified entry in the local report, it reuses the published runnable image without starting a package compilation or verification job. It advertises only verified images. Omit `--owner-secret` on an independent fork, or supply your own secret name. Other supported compiler images are built/verified as before. A fork uses its own Modal account and images.

Private image-routing metadata is written to ignored `.fpm-audit-cache/deploy-routing.json` and included as a file in the API and broker images. Environment variables carry its path rather than its contents, avoiding Windows' 32,767-character environment-variable limit as the catalog grows. This file is separate from package sources, compiled artifacts, and the public catalog.

To process a selected batch, use `--packages fortran-lapack test-drive toml-f`. Previously verified packages outside that batch remain enabled when their library keys still match the current catalog; adding packages does not remove existing ones. This also makes the normal command without `--packages` suitable for catalog additions: only new or changed packages need work. To remove an individual package, remove it from the catalog. To deploy without any precompiled packages, use `--without-precompiled`. Deployment also accepts `--compilers`. A standalone prebuild can use the same `--packages` selection and an optional `--report PATH`.

Use `--reverify` on either command to rerun the changed-main checks while retaining matching compiled libraries. Use `--rebuild` to force recompilation of the selected libraries (all libraries when `--packages` is omitted). The output distinguishes reuse, worker refresh, changed-main verification, and actual library compilation. Missing local reports trigger recovery of published libraries followed by verification; a library is compiled only if no matching artifact exists, its build inputs changed, or a rebuild was explicitly requested.

After deployment, `/api/health` lists enabled `precompiled` package IDs, exact revisions, and `gfortran`. Publish the static page through the repository's normal GitHub Pages workflow. A new page connected to an older service keeps the existing examples and custom URLs usable and explains that precompiled packages have not yet been deployed.

Package updates require an explicit new pin/checksum and rebuild of that package. Transitive dependencies are locked by repository, exact commit, and archive checksum; floating upstream branches are not re-resolved during a catalog build.

`fpm_build_recipe.json`, the GNU build flags, and the build/preparation helpers determine the library recipe. A package's identity contains its source pin, dependency locks, recipe, and any explicit catalog build adaptations or source patches. Descriptions, categories, stars, other catalog entries, browser code, API code, worker updates, and other compiler installers do not invalidate the compiled library. Changes to the compiler or relevant build inputs require new libraries.

Published library images and current worker images are separate. Deployments overlay updated worker code onto each private library image when needed, then verify an edited main before publishing its runnable image. Workers validate the immutable package pin directly, so catalog-only edits do not require updating existing worker images either. No library compilation occurs for that overlay. An example change requires verification of that example, not a library rebuild. Unchanged packages reuse their previous verification by default.

The optional pyplot module is precompiled alongside libraries that do not already supply it, allowing a user to add a plot to a main without regenerating a large dependency archive. No source compilation or cache construction happens during service startup or a visitor's request.


## Additional validation and limits

[Cache-reuse checks](fpm-cache-reuse-validation.json) confirm that compatible libraries are preserved when package metadata, catalog entries, or worker code change. Published libraries can also be recovered without a local report. The checks run edited main programs and verify that the library artifacts remain unchanged.

[The cached plotting check](fpm-cached-plot-validation.json) added a pyplot plot to the stdlib consumer and returned a PNG without rebuilding its library. Ordinary mixed C/Fortran package Build, Run, and Test passed with the updated GNU worker too.

Verification covers the supplied consumer examples, rather than every routine or compiler. The QUADPACK example uses its 15-point Gauss-Kronrod rule. During testing of this pinned build, the 61-point rule returned approximately 0.333333332987796 for the integral of x squared from zero to one, despite requesting 1e-10 accuracy. That discrepancy remains a recorded numerical limitation; the 15-point example passes its explicit accuracy check.

Some candidates remain deferred:

- **ODEPACK:** the pinned version fails the current implicit-interface compilation check.
- **FACE and PENF:** the investigated current source archives failed strict extraction rules. ForPCA and LightKrylov use a pinned older FACE release whose archive passes those rules.

These are limitations of the current preparation/build configuration, rather than claims that the packages cannot work with GNU Fortran. See [candidate selection and exclusions](fpm-catalog-selection.json). Existing support for arbitrary GitHub URLs, other compilers, and clean package workflows remains available under its normal constraints.

To refresh the public measurements after editing examples or adding packages, run `python xprecompile_fpm.py --validation-report docs/fpm-precompiled-validation.json` without `--packages`. This explicitly reruns verification for every package while retaining matching compiled libraries. The report records each example source hash and rejects examples edited after verification.
